# Security of the local server

`testing-hub` is a web server on your own machine. Anything on the machine, and any web page you open in a browser, can
try to talk to it. The guard, the pairing, the sessions, the limits and the engine seam are those of
[appkit](https://github.com/WKDSteve/appkit): **its `SECURITY.md` is the description of what holds for every app, and
its security matrix (`appkit-testkit`, `security_matrix!`) is the shared test of it.** This hub runs that matrix
(`crates/testing-hub/tests/security.rs`): every route of `ROUTES` is a data route, and the matrix tries each one without
a session. This page says what is the testing hub's own.

## What is the testing hub's own

| Thing | What holds | Where it is tested |
| --- | --- | --- |
| Names | App, program, variables, port, routes and login entry are the hub's own and share none with `tasks-hub`, `rules-hub` or the demo app. | `tests/security.rs` |
| Data routes | `fleet`, `repo`, `finding`, `events`, `about`, the five `sheet-step` routes, the five `run` routes and the five `release` routes need a session; a route added to `ROUTES` is a data route by construction. The POST routes (`sheet-step/start`, `sheet-step/command`, `run/start`, `run/task`, `run/abort`, `ci-rerun`, `release`) have the strict rate limit of a mutation. | matrix; `tests/routes.rs`; `tests/sheetstep.rs` |
| The engine only reads, except one run from the page | The hub asks `hello`, `fleet`, `repo` and `finding`, and writes into no repository. The one thing a session may start is a stepped run of a test sheet (`testing sheets step`), which writes no state and no snapshot. The page cannot name a call. | `src/engine.rs` tests; `tests/routes.rs`; `tests/sheetstep.rs` |
| No string from outside reaches the engine | `repo` and `finding` take the key of a repository; the parameters go to the engine as JSON on stdin, never in its arguments. | `tests/routes.rs`; `tests/engine.rs` (real engine) |
| A run from the page: only a known root, only a closed list | `sheet-step/start` takes the key of a repository of the fleet and the name of a sheet (letters, digits, `_ . -`; no separator, no leading `.` or `-`): the root is what the engine names for the key in the local form of `repo`, never a path of the request. `sheet-step/command` takes one of `next`, `continue`, `until`, `break`, `clear`, `answer`, `note`, `explain`, `abort`; the hub builds the line on the child's stdin, a step number is a whole number, the text of an answer is one line of at most 400 printable characters, that of a note one line of at most 1000 bytes, the question of an `explain` one of `what`, `watch`, `result`. The child gets the engine's allow-listed environment plus the trust of roots and the role of the machine from the hub's own environment, so testing.nvim's gates (trust, the workstation) hold as in a terminal; a refusal is the answer of `start`. Beyond that it gets only what the sheet engines and a program a sheet names need to be found (`TESTING_PLAYWRIGHT_DIR`, `TESTING_DESKTOP_DRIVER`, `PLAYWRIGHT_BROWSERS_PATH`, `CARGO_HOME`, `RUSTUP_HOME`). The root of the run is written `<path>` in every text of an event the page reads. | `src/sheetstep.rs` tests; `tests/sheetstep.rs` (a stand-in child that records its stdin); `tests/engine.rs` (the real engine: an untrusted root is refused) |
| A run through the engine: a fixed argv | `run/start` takes the key of a repository of the fleet and optionally a part of a spec file name (letters, digits, `_ . - /`, at most 100, not beginning with `- . /`, no `..`); `run/task` the id of a task (`<area>/<slug>`, the same characters, one `/`) and optionally a key. The argv is a command of a closed list (`run`, `sheets run`), `--root` with the root the engine names for the key, `--file` or `--task` with the checked value (a task's sheets also get the fixed word `--result`, and the hub reads the engine's document `testing-sheet-run/1` from the end of its output: the words `red`, `written` and the outcome of the task, a plain word, never its texts), `--state-dir` with the hub's own state folder, and for a task's sheets `--tasks` with the vault of the tasks when the person named one (`tasks_vault` of `config.json`, `TESTING_DESKTOP_TASKS_VAULT`; a whole path, no default): never a path of the request, never `--trust`. With a vault the engine writes the result into the block of that one task through tasks.nvim, as `:Tasks sheet-run` does, so a phone at the level `trigger` that starts a task's sheets changes that block too; `about` says only whether a vault is named, and the output and the state name it `<path>`. The run of a task is started only when a sheet of the repository has its `task` line, read as text as the engine reads it. The child gets the same environment as a stepped run, so testing.nvim's gates and its queue of heavy runs hold as in a terminal. One run per hub; it ends with the hub, after five hours, and when the page aborts it (`run/abort`, a body that names nothing: no word of a request reaches a process), and then every process it started ends with it (a job object on Windows, the process group elsewhere). The output the page sees is its end, with the root written `<path>`. | `src/launch.rs` tests; `tests/launch.rs` (a stand-in that records its argv); `tests/phone.rs` |
| A run leaves no path and no file of its own choosing on the page | `root` and `path` of `start`, `image` and `shot` of `step-after` are taken out before the page sees an event; a picture is asked for by size and step (`sheet-step/image?size=&n=&kind=`), and the hub serves only the file the child named for that step (PNG or JPEG, at most 16 MiB). A request that names a file is refused. | `tests/sheetstep.rs` (a file of the root the child never named is not served) |
| A release is the engine's, of the commit that was shown | The release assistant (`release/*`) asks the steps of testing.nvim's `testing ci release ... --json` and reads its one document (`testing-ci-release/1`): the hub never reads or writes the list of reviewed commits, never asks GitHub about a commit, and never decides what is released. The argv is `ci release`, a word of a closed list (`--repos`, `--commits`, `--show`, `--yes`), `--json`, and at most a repository (`owner/name` of plain characters, and one `release/repos` named: the engine's list or the fleet) and a commit id of 40 hex digits: never a short id, a branch, a note, a count, a folder or another option. `POST release` is refused unless the review aid of exactly that repository and commit (`release/show`, answered by the engine for that commit) is the one the hub handed out last, at most fifteen minutes ago; the release spends it. One step at a time, each under a time limit; the child runs outside a checkout. A release is started and runs to its end in the background (`release/outcome` says what became of it): a request that is cut off, or a page that is closed, never ends one half way. Only the stop of the hub ends it, as it ends every child of the hub. A page that cannot read the outcome says that it does not know it, never "released" or "not released". It gets the environment of a stepped run plus where the list is and where `gh` keeps its login (`TESTING_RUNNER_ROOT`, `GH_CONFIG_DIR`, `XDG_CONFIG_HOME`): no token of the hub or of the environment (`GH_TOKEN` is not passed on; `gh` uses its own login). A folder of the machine in a text of the engine is written `<path>`. | `src/release.rs` and `src/releasing.rs` tests; `tests/release.rs` (a stand-in that records its argv, its variables and every release); `tests/engine.rs` (the real engine: the first step); `ui/src/lib/app.release.test.ts`; `e2e/release.spec.ts` |
| A request for an AI is shown, never sent | `explain` asks the run for the request an AI would get about a step. testing.nvim builds it (`testing.sheet.explain`, the same one `E` shows in the editor); it comes to the page on the stream like any line of the run, with the root written `<path>`, and is not kept for a page that comes later. Neither the hub nor the page sends it anywhere: the hub holds no key of a model and has no route to one, and the page only offers to copy it. Nothing is asked or built before a person opens the offer and clicks a question. | `src/sheetstep.rs` tests; `tests/sheetstep.rs` (a stand-in that names a file of the root in the request); `ui/src/lib/app.step.test.ts` (nothing but the one command goes out); `e2e/step.spec.ts` (the real engine, no request to anywhere but the hub) |
| One run per hub, and it ends with the hub | A second start is refused and names the sheet that runs. `abort` and the stop of the hub tell the child `abort` and close its stdin (it then takes its own editor or browser down); a child that does not end within three seconds is killed. A child that writes a line over 1 MiB, or more events than a sheet can have, is ended. No request waits for the child except `start`, for its first event or its end, at most 20 seconds. | `tests/sheetstep.rs` |
| The event stream tells no content | An event of the fleet says that it changed and names no repository; the lines of a stepped run come on the same stream, as the page shows them. A session opens at most four streams, and a session that was closed takes its stream with it. | `tests/routes.rs`; `tests/sheetstep.rs` |
| A change costs one question, a request none | Only the three result files of a project in the state folder wake the scan, so what else writes there (and a page that reads often) does not start processes. | `src/watch.rs` tests; `tests/routes.rs` |
| Data classes fail closed | The hub reads the export form: no absolute path, and only the `public` and `internal` repositories that the `areas.json` of the device names. Without the file none is shown; a private one never. | `tests/engine.rs`; `e2e/app.spec.ts` |
| The GitHub token stays in the hub | From `github_token_file` (for the user only; on other rights, a broken file or a wrong path the start stops) or one `gh auth token` at the start, without a shell and with a time limit. It goes to the engine only in the requests of `fleet` and `repo`, as JSON on stdin: never in an argument or the environment of the child. No answer holds it, and its type has no printable form. `about` says where it came from as a word. | `src/github.rs`, `src/engine.rs`, `tests/routes.rs`, and the specs of testing.nvim |
| GitHub is asked at a fixed rate | However often a page reads, the engine asks GitHub at most once a minute per repository (`remote_max_age`, the stored answers of its CI adapter), with ETags. | `src/github.rs`, `tests/routes.rs`, and the specs of testing.nvim |
| Output of a test is text | Names and output of red cases are written by whatever ran: they are shown as text, never as markup or a link, and hidden and reordering characters are made visible (`⟦U+202E⟧`). | `e2e/app.spec.ts` (a repository with markup, a script link, reordering characters and very long output) |
| The page's policy | The policy of appkit for every page; nothing of this page breaks it. | the matrix; `e2e/app.spec.ts` (no violation in any test) |
| Nothing of a result in the browser | The session is in `sessionStorage` of the tab, and `localStorage` stays empty. | `e2e/app.spec.ts` |
| Accessibility | axe reports nothing on the views in the light and the dark scheme. | `e2e/app.spec.ts` |
| Phones (testing mobil) | A phone pairs once with a key of its own (appkit's devices), comes through Tailscale Serve (`tailnet_name`) or a tunnel to loopback, and reaches only `fleet`, `repo`, `finding`, `about`, `run` (cut: a run of anything but a task's sheets is only "another run") and `run/task-sheets` (level `read`), and `ci-rerun` and `run/task` (level `trigger`, confirmed on the phone per request); every other route, `run/start`, `run/abort`, the five `sheet-step` routes, the five `release` routes and `events` among them, answers it `not_for_devices`. No route a phone reaches releases a commit, and no route of the hub trusts a root or runs a command of the request. | `src/phone.rs` tests; `tests/phone.rs` (the matrix with phones, the tailnet, a phone that reads and reruns only confirmed) |
| `ci-rerun` | Takes the key of a repository of the fleet and nothing else; starts the failed jobs of the run the fleet names for it again with `gh run rerun <id> --failed -R <owner>/<repo>` (an argv, no shell, input closed, 30 s), only when that run failed, was cancelled or found no runner. A run GitHub refused (`rejected`) is not started again. A job the runner guard refused is released on the PC (the release assistant, or `testing ci release`), which starts its runs again. | `src/rerun.rs` tests; `tests/phone.rs` |
| Notices | While a phone has subscribed (appkit's Web Push), the hub reads the fleet every five minutes and tells it when a repository turns red: the kind and its key, nothing of a case. | `src/alarm.rs` tests |

## The web variant

`testing.html` has no server to guard; what holds for it:

| Thing | What holds | Where it is tested |
| --- | --- | --- |
| No request | Its policy forbids every request (`connect-src 'none'`), with no WASM and no worker; the sources name no way to one. | `ui/web/web.test.mjs`, `ui/e2e-web/` (every test counts them) |
| No `eval` | The check of the documents is compiled ahead of time from the schema of the contract. | `ui/web/web.test.mjs` |
| Never half an export | Every file is checked against its size and sum in the manifest and against the contract before anything of the export is used; a read that fails leaves the page on the export it holds, and says so. A higher version of the contract is refused by name. | `ui/web/folder-source.test.ts`, `ui/e2e-web/` |
| Only the export form | A document that is not in the export form (it could hold absolute paths) is refused. | `ui/web/folder-source.test.ts` |
| A recorded run is checked line for line | A folder with `events.jsonl` and no export is the recording of a stepped run. Every line is checked against the contract `testing-sheet-session/1` (compiled ahead of time, as for an export) before anything of it is shown; a higher version is refused by name, a line that is none with its number and the rule, never its text; at most 16 MiB and 20000 lines. An export in the same folder wins. Nothing of it is run: the page has no way to a command. | `ui/web/recording.test.ts`, `ui/web/web.test.mjs`, `ui/e2e-web/replay.spec.ts` |
| A picture of a recording is a file of its folder | A picture is read only when its tile shows, only when a line of the recording named it for that step, and only by a plain file name of the chosen folder (PNG or JPEG, at most 16 MiB): a name with a separator or `..` names no picture. It is drawn into a canvas, as on the hub. `notes.json` (which names the root of the repository) is not read. | `ui/web/recording.test.ts`, `ui/e2e-web/replay.spec.ts` |
| One database | Every local file shares the origin `file://`: the page opens only its own database `testing-web`, for the handles of its folders, and never another page's. Nothing of an export is kept in the browser. | `ui/web/web.test.mjs`, `ui/e2e-web/` |
| Foreign text | As on the hub: text, never markup; a link only to a CI run of GitHub. | `ui/e2e-web/` |
| A list saved as CSV or JSON | On the hub and in the web variant, the runs a repository's history shows can be saved: a download of what the page already holds, made in the page (no request, no folder written by the page). A cell of the CSV that a spreadsheet would read as a formula (`=`, `+`, `-`, `@` first) gets a `'` in front, since the ids of red cases come from the tested code. | `ui/src/lib/model.test.ts` |

That the browser keeps a folder over a restart (the fake folder of the tests does not clone) is checked by hand.

## What it does not do

- It is not a defence against someone who already runs code as you: they can read `control.secret` and the state of
  testing.nvim.
- It runs no test of its own, and it does not write into a repository. What it starts is testing.nvim's own command
  line, in a repository of the fleet, under testing.nvim's gates: a stepped run of a test sheet (writing no state), a
  run of a suite, of spec files or of a task's sheets (recording its result as a run in a terminal does). The other is
  GitHub's: the failed jobs of a red CI run started again
  (`ci-rerun`), which runs on GitHub's runners or yours under the runner guard, as a rerun from the web page would.
- It does not decide what the self-hosted runner may run. The release assistant hands the commit a person chose and
  looked at to `testing ci release`, from a session of this PC; the list of released commits and the guard that reads
  it are testing.nvim's. Whoever has a session of the hub on this PC can release a commit, as whoever has a terminal
  can.

## The CI of this repository

The workflows run on the maintainer's own machine. They start only on a push to `main`, by hand, on a pushed tag, or on
a finished CI run of such a push; none has a `pull_request` or `pull_request_target` trigger, and a fork pull request
needs the maintainer's approval (`docs/RELEASING.md`, *The runner*). Actions are pinned by commit.

## Reporting

A hole in the guard belongs to appkit (see its `SECURITY.md`); one in what this page lists belongs here. Open an issue
without the details, or write to the maintainer.
